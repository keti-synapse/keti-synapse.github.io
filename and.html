AND

Adaptive Network Daemon

tom_and_gerri 레포의 _and_/ 모듈이다.로봇 내부의 in-process 버스(pypubsub)와 외부 전송 백엔드를 잇는 얇은 어댑터 데몬으로, 제어 로직은 없고 전달만 한다.

네트워크 데몬 WebRTC Transport 독립 pypubsub
Definition & Role

전달만 하는 어댑터 — 이제 진짜 데몬

AND는 “로봇이 바깥과 어떻게 통신하는가”를 한 곳에 가둔다.GERRI(제어 SW)는 전송 수단을 전혀 모른 채 표준 토픽으로만 말하고, AND가 그것을 실제 네트워크로 옮긴다.

Adaptive Network Daemon — synapse 내부 버스와 외부 transport 백엔드를 잇는 레이어다.

AND는 두 조각으로 나뉜다. 브리지(daemon.py의 AdaptiveNetworkDaemon)는 synapse 토픽 Topic.Network.SEND/Topic.Network.RECV와 백엔드를 잇고, 백엔드(backend.py의 NetworkBackend 인터페이스 + 구현)는 실제 전송 수단을 담당한다 — WebRTC(rtc2kng), nexus 직결 WS, rubberneck, 테스트용 loopback 등.

내부 버스는 pypubsub(in-process·동기 디스패치)이다. 문서는 오랫동안 브리지를 "제어 로직 없음 — 전달만"이라 적어놨지만, pub.sendMessage가 동기라 전달이 곧 실행이었다. 수신 쪽은 백엔드의 WS/asyncio 루프 스레드가 capability를 끝까지 떠안았고(IK 격자탐색 실측 604~800ms·SAM·VLM 수 초) — 현장에서 "누르면 바로 끊겨"로 나타났다. 송신 쪽은 backend.send가 발행 스레드에서 돌아 "누르면 잠시 멈췄다 진행해"였다.

그래서 RX/TX를 독립 워커 스레드로 끊었다(전 로봇 기본 ON). 데몬당 데몬 스레드 2개 — and-rx-<tag>(RX 큐 → Network.RECV, 단일 워커라 FIFO 순서 보존)와 and-tx-<tag>(TX 큐 → backend.send)를 connect()가 띄우고 disconnect()가 접는다. 제리에 무엇을 구현하든 송수신은 영향받지 않는다 — 종전에 ai_chat 하나를 스레드로 뺐던 것을 브리지 한 곳에서 전역으로 해결한 셈이다.

⛔ STOP은 큐를 우회한다: 그 자리에서 인라인으로 발행하고, 밀려 있던 비-STOP 명령은 purge한다 — 밀린 명령 뒤에서 기다리는 STOP은 STOP이 아니다. base의 _handle_for_self 계약은 불변이다.
백프레셔 — 무엇을 합치고 무엇을 절대 안 합치나: 큐는 bounded(256)다. status는 포화 시 가장 오래된 것부터 coalescing한다 — 옛 스냅샷은 새 것이 완전히 대체하기 때문이다. 반면 명령·이벤트는 절대 합치지 않는다(무손실 우선). 모든 폐기 경로가 건수·식별자를 로그로 남긴다 — 조용한 드롭은 없다. 튜닝은 AND_RX_QUEUE·AND_TX_QUEUE·AND_*_FULL_WAIT.
접을 때의 비대칭 · 방어의 시점: disconnect()는 남은 송신을 배출하고(마지막 status 유실 방지) 수신은 폐기한 뒤 접는다. 교차오염 방어 deepcopy는 enqueue 시점으로 못박았다 — 워커에서 뜨면 큐 대기시간만큼 창이 넓어져 방어가 무의미해진다. 회귀망은 상수 비교가 아니라 거동으로 짰다 — 느린 핸들러·느린 send를 실제로 물리고 반환 시간을 잰다(13개).
Bridge

내부 버스 ↔ 외부 전송

Figure 1. AND 브리지 양방향 배선. 송신: Base가 Network.SEND 발행 → TX 큐 → 워커가 backend.send() 호출. 수신: backend가 외부 메시지 수신 → RX 큐 → 워커가 Network.RECV로 재발행. 내용은 변환·검증 없는 pass-through이고, 달라진 것은 어느 스레드에서 실행되는가뿐이다(STOP만 인라인).

방향흐름
송신Base가 Topic.Network.SEND로 발행 → 브리지가 구독하고 있다가 TX 큐에 넣고 즉시 반환 → and-tx 워커가 backend.send(message) 호출
수신backend가 외부 메시지 수신 → 주입된 콜백이 RX 큐에 넣고 즉시 반환 → and-rx 워커가 Topic.Network.RECV로 재발행 → Base가 받아 처리
STOP큐 우회 · 인라인 발행 + 밀린 비-STOP 명령 purge
내용은 여전히 pass-through. 브리지는 메시지를 변환·검증 없이 그대로 넘긴다 — 달라진 것은 실행 스레드와 포화 정책뿐이다. 생성 즉시 SEND 구독이 활성화되고 외부 수신 콜백이 백엔드에 주입되며, connect()/disconnect()는 전송 계층의 수립·정리를 백엔드에 위임한다(그리고 워커 2개를 띄우고 접는다).
Transport-Agnostic

전송은 갈아끼울 수 있다

이것이 AND 존재 이유다.GERRI는 오직 Topic.Network.SEND/RECV하고만 대화하므로, 전송 백엔드를 WebRTC에서 다른 것으로 교체해도 GERRI 제어 로직은 한 줄도 바뀌지 않는다.

NexusWsBackend · nexus 직결 WS (제어 기본) Rubberneck · ketirtc 미디어 (영상) RobotManagementInterface · 로컬 웹 UI (관제망) Rtc2kngBackend · WebRTC 옵션 ↔ LoopbackBackend · 테스트 MQTT?
모두 동일한 NetworkBackend 인터페이스(connect/send/disconnect + _deliver)를 따른다 — 이미 여러 실 백엔드가 공존한다(제어 WS·미디어·로컬 웹 UI, WebRTC는 옵션). config-driven networks.py의 kind는 nexus·rubberneck·rmi.

Figure 2. 전송 독립. 백엔드만 갈아끼우면 된다(브리지·제어 코드는 불변 — 클린 아키텍처). 제어(컨트롤플레인)는 NexusWsBackend(nexus 직결 WS)가 기본이고, 미디어(영상)는 rubberneck(ketirtc)/WebRTC가 맡는다. robot-first WebRTC(rtc2kng)는 WebRTC 옵션 백엔드로 두고, 로컬 웹 UI(RMI)도 하나의 관제망이 된다. 단위 테스트는 실제 네트워크 없는 LoopbackBackend로 대체한다.

인터페이스 계약은 단순하다. 구현체는 connect()·send(message)를 채우고, 외부에서 메시지를 받으면 부모가 제공하는 self._deliver(message)를 호출해 브리지로 올린다. disconnect()는 추상 강제가 아닌 선택(no-op 기본) — 연결·전송은 필수, 정리는 선택이라는 의도적 비대칭이다.

Multi-Network

교체만이 아니다 — 여러 관제망 동시 접속

백엔드는 '갈아끼우는' 것에 그치지 않는다. 신규 _and_/networks.py는 한 로봇이 여러 관제망에 동시에 접속하게 한다 — 데몬을 망마다 하나씩 세우면, 브리지가 pypubsub로 Network.SEND를 구독하는 성질 그대로 송신은 전 망으로 팬아웃, 수신은 어느 망에서 오든 Network.RECV로 병합된다.

rtc2kng

WebRTC 백엔드 — robot-first P2P

_and_/rtc2kng/는 WebRTC 옵션 백엔드다 — 제어 기본값은 nexus 직결 WS(NexusWsBackend)이고, 이쪽은 P2P 저지연 경로가 필요할 때 고른다.로봇이 부팅 시 시그널링에 합류하고, operator의 ready를 받으면 로봇이 offer를 주도한다.단일 asyncio 루프(데몬 스레드)에서 1:N operator 연결을 관리한다.

signaling.py
SignalingClient — WebSocket 시그널링 클라이언트. SDP offer/answer·ICE candidate의 전송 계층만 담당. P2P가 열리면 데이터 경로에서 빠진다.
peer_connection.py
RobotPeerConnection — operator 1명과의 aiortc 연결. ICE 협상 + DataChannel("synapse")로 표준 메시지(JSON) 교환. ice_servers를 주면 RTCConfiguration으로 넘겨 TURN 릴레이를 쓰고, 없으면 aiortc 기본 STUN.
rtc2kng_backend.py
Rtc2kngBackend — NetworkBackend 구현. robot-first, 여러 operator와 동시 1:N. asyncio 루프 스레드에서 시그널링·peer 구동. 연결을 만들 때마다 nexus /api/ice를 재조회한다 — coturn 시간제한 크리덴셜은 만료가 있어 캐시할 수 없다(실패 시 기본 STUN 폴백).
camera_track.py
CameraSource → VideoStreamTrack 어댑터. get_frame()의 BGR ndarray를 av.VideoFrame(bgr24)으로 감싸 aiortc 트랙에 addTrack한다 — 실제 영상 송출 배선 완료.
공유 카메라 허브. 컨벤션은 물리 카메라 1대 = CameraSource 1개 — 한 장치를 딱 한 번 열고(캡처 1회), rtc2kng·rubberneck 등 여러 전송 소비자가 같은 인스턴스를 받아 구독한다(같은 장치 이중 open=device busy 방지, 소유권은 여는 쪽=러너). 제어 버스에 고빈도 프레임을 싣지 않는다 — 영상은 미디어 경로(WebRTC 트랙)로 흐르고, Network.SEND/RECV 제어 채널에는 status·명령 같은 저빈도 JSON만 오간다.
Video Paths

로봇 영상이 관제에 닿는 두 경로

카메라·마이크가 관제에 닿는 길은 둘이며, 데이터·제어(NexusWsBackend의 WebSocket JSON)와는 별개 레이어다. 온보딩에서 "rubberneck엔 뜨는데 콕핏엔 안 뜬다"로 헤매는 지점이라 설계에 명문화했다.

[A] rtc2kng — 콕핏 1:1 (P2P)
로봇이 nexus room에 {robot_id}-cam peer로 합류하고, operator가 1:1 콕핏에 들어오면 WebRTC로 직접 받는다. 러너 config의 camera(또는 --camera)가 있으면 켜진다. ICE는 nexus /api/ice(STUN/TURN·coturn).
[B] rubberneck — 릴레이
로봇이 rubberneck.kr로 올리고 그쪽 뷰어/operator가 받는다. networks의 rubberneck 항목(video_info/audio_info·api_key)으로 켜진다 — 서버를 거치므로 P2P보다 지연이 있지만 망 제약에 강하다.
한 로봇이 A·B를 동시에 쓸 수 있고 같은 카메라를 공유한다 — 위의 공유 카메라 허브가 캡처 1회·다수 구독을 보장하므로 "경로마다 카메라를 따로 열어야 한다"는 오해다(device busy 충돌 없음). 콕핏에 띄우는 게 목적이면 A, 외부 뷰어·릴레이가 목적이면 B — 콕핏에 영상이 없다면 대개 B만 켜진 것이다. 함정: nexus 콕핏은 관례상 단일 카메라 기준이라 멀티캠은 rtc2kng 다중 카메라 지원이 전제다.
operator ready → robot offer → operator answer → candidate 교환 → P2P 직결

Figure 4. robot-first 핸드셰이크. 시그널링이 끝나면 미디어·제어는 P2P로 직결되고 서버는 데이터 흐름에서 빠진다. aiortc는 non-trickle이라 로봇 ICE 후보를 offer SDP에 한 번에 담는다.

🔊 오디오 트랙 — 경로 A가 소리도 나른다: 콕핏은 이미 nexus 직결 P2P를 상시 유지하므로(영상 유무와 무관) 소리도 여기로 간다 — rubberneck을 켜야만 소리가 나는 것은 "기본"이 아니다. ⚠️ 그리고 오디오가 영상을 막지 않게 만드는 것이 설계의 절반이다 — rubberneck이 정확히 그 함정에 빠졌었다(오디오 채널을 모듈 최상단에서 import해서 portaudio 없는 로봇이 영상·command까지 잃었다). 지금은 오디오 모듈이 의존성 0으로 import되고, 비디오를 먼저 붙인 뒤 오디오는 자체 try로 감싸며, 마이크 실패는 전용 예외라 호출자가 오디오만 생략한다. audio_device=None(미사용·기본)과 ""(기본 장치)를 구분하고, 이름을 줬는데 못 찾으면 실패한다 — 기본 장치로 떨어지면 지정한 게 아닌 소리가 나간다.
MediaRelay — 오퍼레이터가 N명이어도 인코딩은 1회: 실기에서 "멀티유저일 때 서로 가져가서 둘 다 끊긴다"는 관측이 있었다. 원인은 캡처가 아니라 인코딩이었다 — 캡처는 이미 1-owner 스레드가 공유했는데, 오퍼레이터마다 새 트랙을 붙여 같은 프레임을 N번 인코딩했다. 실측(x86 640×480 프레임당) VP8 1.40ms·H.264 0.90ms → 오퍼레이터 5 × 카메라 2 = 18.6ms로 33.3ms 예산의 55.9%다. Orin에서 3~5배면 3명×2대가 이미 넘친다 — 그게 "둘 다 끊긴다"의 정체였다. aiortc MediaRelay로 소스당 relay 1개·오퍼레이터마다 구독으로 바꿔 비용을 오퍼레이터 수와 무관하게 만들었다(검증: 4명 × 5프레임 = 20 요청 → 실제 카메라 pull 5회).
고정 주기 캡처 — 처리율이 아니라 꼬리 신선도: 캡처 루프가 _read() 뒤에 무조건 sleep(interval)했는데, 그건 _read가 공짜라는 가정이다 — 블로킹 백엔드에선 거짓이라(RealSense wait_for_frames()) 한 주기를 기다린 뒤 또 한 주기를 잤다. 실측(D415 640×480@30): 처리율 이득은 작았지만(28.4 → 29.8Hz) 프레임 나이 p95가 31.7 → 21.6ms(−32%)다 — 종전엔 20프레임 중 1개를 한 주기 통째로 낡은 채 넘겼다. "프레임률이 절반 된다"는 앞선 추측은 실측으로 반증됐다. 프레임에 seq·age 신원을 붙여 소비자가 낡음을 판정할 수 있게 했다.
Latency Reporting

3-링크 지연 실측 — status에 자동 주입

AND는 전달만 하는 데 그치지 않고, 각 통신 링크의 왕복 지연(RTT)을 실측해 robot.status.network에 자동으로 채운다. 로봇별 코드 없이 synapse의 NetworkState 계약이 충족된다.

server 링크
NexusWsBackend ping/pong — 주기 ping(TimeSyncSlave 4-타임스탬프)으로 서버 RTT + 시간 offset 측정. keepalive 겸용.

InternetProbe — 공용 앵커 목록에 TCP 핸드셰이크 RTT(ICMP·권한 불필요). 프로세스 공용 싱글턴으로 주기 갱신. 기본 앵커는 사업자·포트를 섞은 셋(1.1.1.1:53 · 8.8.8.8:53 · 8.8.8.8:443)이고, 첫 성공 앵커의 RTT를 쓰되 전부 실패해야 끊김으로 본다 — 단일 앵커는 특정 IP만 막는 방화벽에서 오탐이었다(실측: 내부망이 1.1.1.1만 차단).

Gateway Rule

Sub는 네트워크를 직접 만지지 않는다

AND/외부 토픽에 손댈 수 있는 것은 오직 Base(게이트웨이) 하나뿐이다.SubController는 외부 통신을 전혀 몰라야 한다.

규칙: SubController는 Topic.Network.SEND/RECV 등 외부 토픽을 직접 사용하는 것이 금지된다.Sub는 자기 status를 내부 토픽으로만 발행하고, 외부와의 모든 송수신은 Base가 단일 창구로 중계한다.이렇게 해야 전송 교체가 Sub에 전혀 영향을 주지 않고, AND의 “전달만 하는 데몬” 경계가 유지된다.

즉 의존 방향은 Sub → (내부 토픽) → Base → (Network.SEND/RECV) → AND → backend → 네트워크 한 방향으로 흐른다. Sub가 이 규칙을 어기고 외부 토픽을 직접 건드리면 게이트웨이 정책이 깨지고, 백엔드 교체 시 Sub 코드까지 수정해야 하는 결합이 생긴다.
